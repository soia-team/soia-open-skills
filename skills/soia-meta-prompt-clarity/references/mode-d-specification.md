# 复杂请求规格化

仅对本次真正复杂的范围使用。目标是完整可执行的提示词，不是另建治理系统；语言、安全和默认只产出边界仍按主入口。

## 保留要求，补足验证

从原始请求提取明确要求，沿用其顺序或稳定标识。识别事实、目标、限制与未知；每项强制要求都能回到提示词中的条款和验收方法。

结构可以创造，事实不能创造。字段、切片、状态或验收方法可按任务设计；模型、价格、CLI 参数、已有路径和历史能力必须有已读材料，或留给执行者现场探测。用户已委托的结构选择不反问回去。

- 全部对象：先明确可枚举边界，盘点实际集合，再定义完成状态；不静默抽样。
- 自动选择：写决策因素、用户覆盖权和无候选时的结果，不降为只给建议。
- 避免降级：区分请求值与实际值，缺少证据就是未验证；不静默换执行器或 provider。
- 费用：计量来源、未知值和预算门明确；API 等价估算不能冒充订阅实际扣费。
- 恢复/重试：只对相关副作用说明幂等、部分成功、断点与停止条件，不每次新增持久状态。
- 验证：给可观察结果与失败路径；不能只把“必须正确”写得更长。

这些是可选转换方向，不是每份提示词的必填字段。

## 原料与澄清

已粘贴内容可引用；只给路径/URL但未读时要求未来执行者读取，不能冒充已知事实。只有缺口改变意图、输出、授权、公共契约或不可逆范围才暂停；可探测事实、显式占位或次要细节不阻止完整产出。

不通过删需求解决冲突。未决、拒绝或用户批准延期的项明确说明，不能悄悄消失。复杂要求可用短表对应原要求与条款；不强制固定状态枚举、八阶段流程或七字段回执。

## 涉及技能开发时

安装目录、软链接与 lock 的来源记录不证明本机源码 checkout。使用给定 source repo；未给则让执行者核实带 Git 的真源和 remote。先源码修改与验证，再按授权提交/发布，从正式远端验收安装；本地调试不冒充远端正式安装。

不得一边要求远端验收，一边无条件禁止同一流程必要的已授权 push；授权不足时明确停在哪一步，不能自行获得新权限。通用规格化不替代目标项目的准入与不可回退边界。

## 交付前

按[主入口直接链接的质量门](mode-d-quality-gate.md)检查要求忠实度和实际可执行性。先交完整提示词，再给必要的需求对应与未知项；不要求用户阅读全部分析过程，不固定说明篇幅。
